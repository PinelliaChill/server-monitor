# 节点瞭望 · 服务器监控

一个中文服务器监控演示面板，使用 React、TypeScript、Vite 和普通 CSS。所有数据在浏览器内模拟，无需后端、API 密钥或环境变量。

[在线演示](https://server-monitor-demo-bigo.workspace-169790.chatgpt.site)

## 快速运行

先安装 **Node.js 22 或更新版本**（包含 npm）和 **Git**，然后在终端执行：

```bash
git clone https://github.com/PinelliaChill/server-monitor.git
cd server-monitor
npm ci
npm run dev -- --host 127.0.0.1 --port 5173
```

浏览器打开 [http://127.0.0.1:5173](http://127.0.0.1:5173)。若端口被占用，以终端实际输出的地址为准。按 `Ctrl+C` 停止服务。

## 测试与构建

以下命令均在项目目录中执行：

```bash
# 运行测试
npm test

# 类型检查并生成生产文件
npm run build

# 预览生产版本（先完成构建）
npx vite preview --host 127.0.0.1 --port 4173
```

生产预览地址为 [http://127.0.0.1:4173](http://127.0.0.1:4173)，若端口被占用，以终端输出为准。构建产物位于 `dist/`，可部署到静态网站托管服务。

## 功能与数据规则

- 展示 5 台服务器，每 2 秒独立更新 CPU 和内存，在上次数值上随机增减 −5～5 个百分点，限制在 0～100%。
- 状态由 CPU 和内存的较高值决定：低于 80% 为正常，80%～不足 90% 为警告，90% 及以上为严重。
- 支持状态筛选、CPU 升降序排序，列表随数据实时更新。
- 点击卡片或使用 `Enter`、空格键展开详情，支持多卡展开，排序及筛选后保留展开状态。
- 详情包含服务器 ID、运行时长及最近 60 秒的 CPU／内存趋势，仅保留实际模拟采样，最多 31 点。
- 支持手机布局和减少动态效果设置。重新加载页面会恢复初始数据并重新积累趋势。

### 一、项目创建

我选择在 codexworkspace 下新建一个项目空间，以此保证环境的干净，防止 agent 被不必要的 AGENTS.md 与记忆干扰。

### 二、多 agents 的考量与模型的选择

为了保证效果，我需要保证 agent 的上下文简洁，于是决定使用 subagents 起到隔离上下文的作用；同时，让他们并行执行，进一步提高效率。

此时问题又出现了：coder 模型需要几个？需不需要单独的 reviewer？考虑到这次的编程任务相对简单，又使用模拟数据，区分前后端或者多个 coder 并行导致新增的沟通成本，很可能会大于其带来的效率提升，导致耗时反而增加、效果下降。

单独的 reviewer 我认为还是需要的。LLM 都有这个问题：如果让同一个模型检查自己写的代码，稍微复杂一些的问题就会找不出来。所以我只让 coder 做简单的测试。这种代码层面的简单测试交给 reviewer，需要其再完整阅读一遍代码，coder 做就很迅速。reviewer 模仿真实场景检查功能，更容易发现代码上发现不了的问题。

考虑到时间限制，思考强度不能选择太高。但是，如果一味降低，最终可能需要反复更改，反而时间更长、效果不好。于是，我选择了 gpt6.1sol-high 作为主 agent 的模型。而对于这种简单的任务，coder 与 reviewer 能力可以差一些，于是为了进一步减少耗时，我选择了 medium 思考强度。同时，我开启了 fast 模式。

### 三、提示词的编写

提示词工程中最重要的，就是讲清楚自己的需求。而随着模型能力越来越强，不需要通过大量的例子来说明自己的需求。不论是 Anthropic 还是 OpenAI，都有研究表明冗长的提示词会导致模型能力下降。现在的提示词工程中，简要地说明自己的需求就格外重要了。

1. 为了让其获得详细的需求信息，我剔除无关信息后，把相关信息都复制进去了。
2. 因为大量信息都是英文，若此时不明确要求，很可能会使用英文输出并搭建网站。为了方便阅读，我明确规定使用中文。
3. `/grill-me` 是让 agent 向用户提问不确定的需求与问题，达到对齐效果，防止 agent 在不明确的地方过于自由发挥。
4. `/plan` 可以开启 Codex 的计划模式。在执行前先输出计划，可以确定 agent 的方案会不会与设想有太大出入，同时提前确定大方向，减少 agent 走一步看一步的情况，提升效果。
5. 因为使用了 subagents，3 个模型之间的沟通很大程度上会决定耗时、上下文质量与最终效果，这是值得专门写一条规则的。LLM，尤其是 GPT 系的通病，就是喜欢使用冗余与晦涩的措辞，特别是在 agents 之间的沟通。这种效应会滚雪球式叠加，导致越来越冗余与晦涩，所以需要针对其痛点写提示词。
6. 因为要展示，所以我让其做完后发布成 Site，这是 Codex 的一个功能，可以方便地创建网站。

### 四、运行时

1. 提示词刚发送，我发现忘记开启 `/fast` 了。Codex 任务运行时再开启很有可能检测不到，于是我重新启动了一次。
2. agent 使用 `/grill-me` 询问了我几个问题。挑一个关键的选择来讲：选择 UI 的色调为浅色调。考虑到时间限制，浅色调更容易做出相对美观的界面，不需要反复修改。
3. 我浏览了计划，确保问题不大，允许执行。
4. 在运行过程中，我重点关注各 agent 有没有偏离方向，以便及时纠正，同时查看其之间的沟通是否简洁。前面编写的提示词还是效果不错的。
5. 在网站出来后，我进行了测试，重点测试了几个需求有没有达到。

至此，任务完成。
